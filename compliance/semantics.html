Semantics and open questions

What was implemented, what remains different, and what to ask STACK

The comparison uses STACK revision 10d323311b7f39fb7b092dd10ce75f7d8632f525. Case numbers below refer to the unchanged 2,303-row imported fixture. An expected acceptance is a statement in that fixture, not automatically a universally valid complex identity. Native agreement and mathematical correctness are separate axes.

How to read the evidence

Four questions are kept separate throughout this page:

Axis What it establishes
Mathematical claim Whether the expressions agree under stated domain and branch assumptions.
Fixture expectation What the imported STACK row asks the test to return; it is evidence of the intended test outcome.
Native observation What the pinned STACK/Maxima run actually returns. This is not automatically a mathematical proof.
Port behavior What the bounded SymPy implementation returns or explicitly declines to support.

Documented convention means that a STACK source explicitly prescribes a behavior. Observed behavior records an implementation result. Proof or normalization limit means that a test does not establish an equality. Port boundary means that this implementation deliberately rejects an input or operation it cannot preserve. An engineering explanation is labeled as such; it does not turn an observation into an explicit convention.

The collection trace below uses Maxima 5.46.0, the pinned STACK revision above, port revision 1e72245874bfea49836e58ba48dcee30af5ee0ba, and SymPy 1.13.3. The report remains about the bounded CAS adapter, not all Moodle controller or question-state behavior.

Implemented scalar and written-form behavior

Written form: cases 645, 647, 658, 665 and 2278

Evidence: documented written-form contract and observed native fraction handling.

EqualComAss checks more than mathematical value. STACK’s rule-based test documentation explains that division is held as a numerator multiplied by an opaque reciprocal. The port now preserves that structure:

Cases Submitted / reference Expected result and reason
645 x/(-y) / -(x/y) Reject: a minus inside the reciprocal differs from an outer minus.
647 1/2*1/x / 1/(2*x) Reject: separately written fractions differ from one reciprocal of a product.
658 (1/2)*(a+b) / (a+b)/2 Reject: a rational coefficient differs from a held division of the whole sum.
665 1/3*i / i/3 Reject for the same written numerator/reciprocal distinction.
2278 x-1/-4 / an ignored reference Reject: when extracting numerical fractions, the outer subtraction gives a negative numerator over a negative denominator.

The final case is not a ban on negative denominators. Native LowestTerms accepts 1/-3 and x+1/-4, while rejecting -1/-3 and x-1/-4. This follows list_expression_numbers and lowesttermsp. It continues to ignore the reference value and does not cancel polynomial factors.

Floating-point constants: cases 32, 37 and 43

Evidence: observed native arithmetic, documented floating-point context, and bounded port emulation.

STACK’s numerical-rounding documentation describes binary floating-point artifacts and recommends numerical tests for approximate answers. The port reproduces the following literal-constant cases with finite binary64 arithmetic and exact equality of the resulting machine values:

Case Submitted / reference Native-compatible result
32 452 / 4.52*10^2 Reject: the multiplication produces approximately 451.99999999999994.
37 0.99999999 / 99999998/99999999 Accept: both map to the same binary64 value; the exact rational values differ.
43 100.4-80.0 / 20.4 Reject: the subtraction produces approximately 20.400000000000006.

Case 37 also has a direct explanation from the STACK author in issue 1581: Maxima’s rational conversion of a float need not recover its decimal fraction. The discussion separates exact mathematical notation, finite machine precision, and the difficulty of inferring a student’s intention. The port’s bounded binary64 comparison reproduces these cases; it does not implement Maxima’s general rat algorithm or claim all floating-point behavior agrees.

This compatibility path applies only to AlgEquiv with literal arithmetic, at least one decimal/scientific literal, and integer exponents. Symbols, functions, and frozen author values retain the symbolic path. The shared parser still evaluates decimals as exact rationals; numerical tolerance tests retain their own tolerances. There is no epsilon-based algebraic acceptance.

Reciprocal square roots: case 80

Evidence: an explicit STACK convention, reproduced within a stated port boundary.

The installation notes explicitly require 1/sqrt(x) and sqrt(1/x) to count as equivalent, while acknowledging the domain debate. The port now implements that symbolic convention for a top-level reciprocal square root of a single symbol. It does not propagate the convention into logarithms, larger products, or ratios. This is a documented STACK compatibility rule, not a general principal-complex identity: at a negative real value the two principal values have opposite signs. Explicit numeric inputs such as 1/sqrt(-1) and sqrt(1/(-1)) remain distinct. Ratios, arbitrary root products, and nested powers are not forced into the same convention.

Principal logarithmic powers: case 166

Evidence: a mathematical proof implemented in the port; no case-specific published STACK rationale was located.

For nonzero x,y, principal powers give

\[x^{\log y}=\exp(\log y\,\log x)=\exp(\log x\,\log y)=y^{\log x}.\]

The port now certifies this through bounded exponential rewriting, a strategy also used in STACK’s equivalence routine. This proof is our mathematical explanation; we did not locate a published STACK rationale for this particular row. It does not expand a logarithm of a product and does not require positive-real assumptions. The earlier description of this case as requiring a different branch convention was too conservative.

Eight domain/branch differences for discussion

All eight currently have a desired/native acceptance and a port rejection. The counterexamples below concern the port’s principal-complex interpretation. They do not establish that STACK intended that interpretation. Where the sources give only a mechanism or nearby context, we explicitly leave the intended contract open rather than claiming the behavior is a deliberate design choice.

Case Identity accepted by STACK What happens under principal-complex semantics Question for STACK
50 i/sqrt(x) = sqrt(-1/x) True for nonzero real x. At x=-i, the sides are exp(3*pi*i/4) and exp(-pi*i/4). Is x implicitly real, or is another symbolic-root convention intended?
76 abs(x) = sqrt(x^2) True for real x; at x=i, the sides are 1 and i. The port already accepts the identity with its explicit real assumption. Should the fixture declare real x?
92 6*((x-2)^3)^k = 6*(x-2)^(3*k) At x=1,k=1/2, the sides are 6*i and -6*i. Is k integral, is x>2, or is odd-inner-power denesting intentional?
99 sqrt(k/m)*sqrt(m/k) = 1 True for positive real k/m; at k=-1,m=1, the product is -1. Should positivity be explicit, or is a broader root-combination rule intended?
101 2*pi*sqrt(m/k) = 2*pi/sqrt(k/m) At m=-1,k=1, the sides are 2*pi*i and -2*pi*i. Is positivity intended, or does the documented single-symbol convention extend to ratios?
127 (-1)^n*cos(x)^n = (-cos(x))^n True for integer n; at n=1/2,x=pi, the sides are -1 and 1. Is n implicitly integral?
155 log(a^2*b) = 2*log(a)+log(b) True for positive real a,b; at a=-1,b=1, the sides are 0 and 2*pi*i. Should positivity be required, or are branch constants ignored?
167 log((x+1)/(1-x)) = -log((1-x)/(x+1)) True on the real interval -1<x<1; at x=2, the sides differ by 2*pi*i. Is that interval intended, or is equality modulo 2*pi*i intended?

Evidence and limits:

  • Defining variables documents explicit assume/declare contexts and the real-style square-root identity relevant to cases 50 and 76. It does not fully specify their bare rows.
  • Simplification explicitly warns against general nested-power denesting without assumptions. That makes case 92 a question to resolve, not permission for a blanket rewrite.
  • The implementation sets logexpand:super, then applies several transformations including radcan. This supplies an implementation mechanism for logarithmic differences, not a per-case mathematical justification for ignoring branches.
  • For 50, 99, 101, 127, 155 and 167, we located fixture expectations and the implementation but no case-specific published rationale. The explanations and counterexamples above are the port team’s analysis, offered for discussion.

Two missing exact proofs

Both source rows use -3: desired acceptance despite a native rejection. The port also rejects them. Agreement between engines does not resolve either.

Case 471 — nested radical. For real x, let u=sqrt(x^2+1)+x. Then u>0 and u^2=2*x*sqrt(x^2+1)+2*x^2+1; hence the outer square root is u and the submitted expression is zero. For complex x=-i it is instead 2*i. The missing work is an explicit real-domain contract and a bounded sign-aware proof. Ask STACK whether the real assumption should be stated in the fixture.

Case 474 — cos(2*pi/17). The reference is its constructible radical representation. This is an exact-real constant identity, not a branch-convention dispute. The port lacks a certified algebraic-number proof with root selection. Numerical agreement would not suffice. Ask whether this exact certification is a useful target and whether STACK has a preferred proof method.

STACK’s equivalence documentation acknowledges incomplete radical proofs and explains why more aggressive generic transformations can lead to expression growth and timeouts.

Reading the report

The eight domain/branch cases and two exact-proof cases above remain case-pinned in the checker policy. Collection normalization differences below are additional observations. The report separates Domain/branch difference from Unproved identity, with explanations, evidence, source links, and questions for STACK. A changed label does not turn a disagreement into a compatibility pass; a changed result invalidates its old exception and must be reviewed.

Finite lists and sets

Which equality is being tested?

Test and objects Native comparison route Current port contract
AlgEquiv, lists Recursively compare corresponding entries with AlgEquiv. The same ordered recursive contract for supported leaves.
AlgEquiv, sets Prepare members with ATSets_prepare, then compare set membership. Compare structural SymPy members, with bounded exact rectangular conversion for certain numeric complex constants.
Sets Related set preparation, with duplicate, extra- and missing-entry feedback. Structural member comparison and outer duplicate feedback; no full scalar-proof matching.
EqualComAss A written-form contract, after applicability/equivalence checks. Preserve written arithmetic, list order and set multiplicity within the supported held-form subset.
SameType Uses ATAlgEquivfun applicability at this pin. Reproduces that applicability behavior; it is not a strict nested-shape validator.

The pinned set routines do not run the full scalar algebraic_equivalence routine on every candidate pair. STACK’s equivalence documentation explains the canonical-representation strategy and the risk of expression growth from stronger generic transformations. This is a documented engineering tradeoff, not a claim that differently represented members must be mathematically unequal.

The port uses its own SymPy normalization, not an emulation of every intermediate Maxima form. For example, it keeps {(x+1)^2} distinct from {x^2+2*x+1} under structural set comparison. Its bounded rational multiple of exp(i*pi*q) can use exact rectangular form under AlgEquiv; this conversion is not applied by Sets. Agreement on selected results does not establish identical normalization.

A trigonometric identity inside a set

Mathematics. sin(x)^2+cos(x)^2=1, so the two singleton sets denote the same set. There is no domain/branch counterexample behind the rejection discussed here.

Observed results. Direct probes of the pinned native and port versions give:

Comparison Native STACK Port
Scalar AlgEquiv: sin(x)^2+cos(x)^2 / 1 Accept Accept
List AlgEquiv: [sin(x)^2+cos(x)^2] / [1] Accept Accept
Set AlgEquiv: {sin(x)^2+cos(x)^2} / {1} Reject Reject
Sets: {sin(x)^2+cos(x)^2} / {1} Reject Reject

These set rejections have CAS applicability true; they are not syntax errors. The project controls port-list-equivalence, port-set-trig-structural, and port-sets-trig separately record the list/set results and Python/Pyodide parity.

What native preparation actually does. The source calls:

ATSets_prepare(S) :=
    ev(map(lambda([ex], ineqprepare(trigreduce(ex))), S), simp)$

For p:sin(x)^2+cos(x)^2, the trace is:

Stage Native result
trigreduce(p) (cos(2*x)+1)/2 + (1-cos(2*x))/2
ineqprepare(trigreduce(p)) The same two-fraction sum.
Ordinary ev(...,simp) in set preparation The same two-fraction sum.
ATSets_prepare({p}) {(cos(2*x)+1)/2 + (1-cos(2*x))/2}
ATSets_prepare({1}) {1}

trigreduce has performed a trigonometric transformation: it rewrites squared sine and cosine using double angles. It has not completed the rational arithmetic that combines the two fractions. Ordinary simplification in this pipeline leaves them separate, and the subsequent membership comparison does not invoke the stronger scalar equivalence test to bridge that gap.

Further native probes establish the missing step:

ratsimp(trigreduce(p));             /* 1 */
expand(trigreduce(p));              /* 1 */
trigsimp(p);                       /* 1 */
ratsimp(ATSets_prepare({p}));       /* {1} */

Comparing the prepared member to 1 using scalar AlgEquiv accepts. Applying ratsimp to the prepared set before either set answer test also changes rejection to acceptance. These are native-CAS probes, not claims that all those author functions are exposed by the port.

How the port differs internally. The port’s prepared submitted set remains {sin(x)^2+cos(x)^2}; its reference is {1}. It does not perform the native half-angle rewrite here, and it does not use its scalar identity prover to match set members. Thus it reaches the same rejection through a different intermediate representation. Scalar and list AlgEquiv use its stronger proof path and accept.

Classification and rationale. This is a set-normalization/proof limit, not an explicit convention that trigonometric identities cease to hold in sets. STACK’s Sets documentation says that authors should preprocess arguments when stronger trig simplification is needed. Its broader documentation explains why automatically applying stronger transformations to all set members can be too costly. Neither source establishes that this particular simple rejection was intentionally selected as a convention.

Question for STACK: is author-side preprocessing the intended contract for this pair, or should bounded set-member preparation establish the identity? A stronger matching mode in the port would be an explicit behavior change, rather than evidence that the existing native set test already performs that matching.

Proposed stronger set-member matching

Status and scope. This is a design proposal, not current port behavior or a claim about native STACK. For bounded flat sets of the scalar expressions already supported, a stronger checker would be a small-to-medium feature rather than a rewrite. The matching algorithm is straightforward; specifying reliable grading and feedback takes more care. Supporting nested collections and predictable computation limits broadens that work. Any stronger mode would need an explicit contract because accepting additional identities changes compatibility with the native set tests described above.

Once duplicate semantics are resolved, the comparison could proceed as follows:

  1. Recognize structurally identical members cheaply and cache those successful comparisons.
  2. Compare remaining candidate pairs using the existing scalar AlgEquiv proof path, under the same domain assumptions. Record proved equal, proved unequal where available, and inconclusive separately. Failure to find a proof is not itself proof of inequality.
  3. Build a bipartite graph whose edges are certified equal pairs, then find a complete matching with a standard polynomial-time algorithm. This does not require factorial permutation search. Structural matches provide the fast path; the final matcher must be able to reassign tentative pairings rather than commit greedily to the first available candidate.

For two flat sets with 32 members each, there are at most 1,024 cross-set candidate pairs. This bounds that comparison phase, not total work: comparing members within each set to resolve algebraic duplicates adds comparisons, and nested comparisons recurse. A single symbolic proof can also be expensive. Symbolic proof work, rather than graph matching, is therefore the principal runtime concern. Cached results and limits on proof work, expression growth and total recursive comparisons would be part of the design; the pair count alone does not guarantee a response time.

The grading contract needs four further decisions:

Issue Required behavior or decision
Algebraic duplicates {sin(x)^2+cos(x)^2,1} denotes the same mathematical set as {1}. A bijection over the raw submitted entries would wrongly reject it. Decide how certified equal members form duplicate classes before testing cardinality or matching, while retaining original entries for Sets duplicate feedback. Incomplete proofs can leave those classes unresolved.
Nested collections Lists remain ordered and compare corresponding entries; sets use the stronger unordered comparison recursively. Preserve list/set type and nesting boundaries. Existing size/depth bounds still apply, with a shared budget across the whole comparison tree.
Inconclusive results Budget exhaustion or an unproved candidate must remain distinguishable from established inequality. Accept only when the necessary equality certificates exist. An unresolved comparison must not be presented as a mathematical counterexample or definitive extra/missing-member explanation.
Written form EqualComAss keeps its separate contract: written arithmetic and repeated set entries still matter. A stronger algebraic check could satisfy its equivalence prerequisite, but must not replace its held-form comparison or erase submitted form.

For Sets, deterministic matching and retained submission provenance would also be needed for useful feedback when several pairings are possible. Missing/extra diagnostics should explain the checker outcome without overstating what an incomplete proof established. A first implementation could target flat exact scalar sets, followed by recursive collections and richer feedback under the same explicitly stated semantics.

Adding ratsimp to preparation would address the traced trig example, but that is a narrower normalization improvement. It would neither implement general scalar-proof matching nor settle duplicates, recursive behavior or proof limits.

Exact constants: mathematical equality versus compatibility

  • 202: {[-sqrt(2)/sqrt(3),0],[2/sqrt(6),0]} / {[2/sqrt(6),0],[-2/sqrt(6),0]}. This is the related radical equality inside list members of a set, not a disputed complex branch identity.

Mathematical equality and compatibility status are separate statements in all four rows.

Question for STACK: is row 212’s expected rejection intended to assert prepared-form behavior, and what normalization should authors expect for mathematically equal set members?

Port design decision: preserving Maxima’s prepared-form distinctions versus using SymPy’s canonical members is a compatibility policy for this project. Faithful emulation for 212 would require held member provenance before SymPy canonicalization. There is no expression-specific grading exception for these cases.

Nested structure and duplicate scope

Lists retain order and repetitions. Nested sets keep their boundaries and use structural normalization recursively; {1,{2}} is not flattened to {1,2}. Lists inside sets retain list order. The port preserves submitted repetitions until the relevant test runs.

Sets duplicate feedback concerns the submitted outer set:

Submitted / reference Result under Sets
{1,1} / {1} Correct; no outer duplicate warning.
{{1},{1}} / {1} Correct, with an outer duplicate warning.

This describes the scope of duplicate feedback, not a general promise to report every repeated leaf in a nested collection.

Written form is an explicit separate contract

EqualComAss documentation explicitly distinguishes {4,4} from {4} as held written forms. Set arguments commute but do not associate, lose multiplicity or flatten nested set boundaries. Thus reordered {1,2,2} / {2,1,2} passes, while {4,4} / {4} fails the form check even though their mathematical set values agree. Nested list order matters.

The port checks applicability and algebraic equality before held form. This is a purposeful form-sensitive contract, unlike an unsuccessful proof of ordinary set-value equality in the trig example. Frozen teacher/qtest aliases that would lose the required written form fail at build time; this is a port preservation boundary, not a native prohibition on those aliases.

Type applicability is observed implementation behavior

At this pin, ATSameTypefun uses the applicability flag from ATAlgEquivfun. The port follows that behavior:

Pair SameType result and implementation reason
[1,[2]] / [9] True: the unequal-list-length path is still applicable.
[1,[2]] / [9,{3}] False: equal-length lists recurse to different member types.
{[1,2]} / {1,2} True: set/set comparison is applicable regardless of member types.

These results are observations of the pinned predicate, not a mathematical definition of nested type or a strict shape-equality guarantee. Collection input checkanswertype follows the same rule. An equality test is still needed for content.

Decimal precision: native observations and port boundaries

The native observations below are distinct from the port’s decision to reject inputs whose precision provenance cannot be preserved.

Context Pinned native observation Port contract
Set {1/10} / {0.1}, or {1/2} / {0.5} Both set tests reject. Decimal literals anywhere below a set are unsupported; use exact fractions.
Direct list [1/10] / [0.1] Scalar/list AlgEquiv accepts. Direct decimal list leaves use the bounded scalar binary64 path.
[100.4-80.0] / [20.4] AlgEquiv rejects. Retain literal arithmetic; freezing the first answer to [102/5] would change the result.
[sin(0.1)] / [sin(1/10)]; [sqrt(0.5)] / [sqrt(1/2)] AlgEquiv rejects. Decimal-bearing function and symbolic list leaves are unsupported; use exact fractions.
[20.4] / ev([100.4-80.0],simp) AlgEquiv rejects. Decimal-bearing transformed collections are unsupported.

The set results are consistent with native float/rational representations remaining distinct as prepared members. They do not establish that {1/2} and {0.5} are different mathematical sets: 0.5 is exactly representable in binary. The port parses decimal tokens as exact rationals, so it cannot simply reuse its structural member keys for all native floating cases and claim parity.

The port therefore imposes these deliberate engineering limits:

  • Decimal list leaves support literal constant arithmetic, unary signs, and bounded integer powers; decimal-bearing functions, symbolic leaves and author transforms require exact-fraction alternatives.
  • Frozen collection/helper definitions reject transitive decimal-valued aliases, including their use in qtests and CASText. Learner collection answers referring to decimal-derived author aliases are rejected too.
  • Dynamic collection sans must directly name the learner input. Collection feedback aliases and learner-dependent collection/helper construction are unsupported because serialization can lose the literal arithmetic.

These restrictions concern the port’s representation and native compatibility; they are not claims that native STACK forbids the same author expressions.

Finite author helpers and held execution

Finite helpers are author-only in the port, with bounded input/output and normal simplification. Their results freeze into question variants:

Helpers Supported port inputs/results
set, setify Construct a finite set; setify takes a list.
union, intersection, setdifference, subsetp, cardinality Supported finite set operations within their arity/resource bounds.
member Membership in a supported list or set.
listify Preserve an existing list, or numerically sort rational scalar set members. Symbolic/complex/nested set ordering is unsupported.

This supported author path requires exact fractions rather than decimal helper arguments. Learners enter collection literals, not helper calls.

The simp:false boundary is a port scope decision. Recorded pinned native probes show why merely reusing normally simplified operations would change held behavior:

Held native probe Observation
setify([1,1]) Keeps held repetitions.
listify({2,1}) Keeps written order.
Membership involving [x+x] and [2*x] Can distinguish their held forms.
Intersection/difference of held sets Can depend on written ordering.

The port does not emulate general held CAS execution. Helper feedback variables, helper calls with question simplification off, and direct helper calls in Sets/EqualComAss fail clearly. Simplified helper results frozen in question variables remain usable by those checks. Direct normal AlgEquiv/SameType author expressions can use the supported helpers subject to the same bounds.

Feedback and the tested layer

The port’s ordinary feedback is abbreviated English. Negative list results do not reproduce every native nested index/reason note, and EqualComAss does not reproduce every internal note. Full localized feedback and exact ordinary notes are not claimed compatible.

Authored PRT branch notes and their ordered qtest expectations are preserved. Neither these bounded CAS checks nor Python/Pyodide agreement establishes full Moodle/PHP-controller, input-security, or attempt-state parity.
